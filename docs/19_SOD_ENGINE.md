# AccessPilot — Separation of Duties (SoD) Engine

**Status: implemented and live.** This document describes the system as it actually works today, not a plan — everything below has been built, tested (65 backend tests in `test_sod.py`, 364 across the whole backend suite), and verified against the real tenant.

## Revision history (newest first)

1. **Real bug found live, one grant after the previous fix shipped: a fresh SoD exception grant got auto-revoked within about a minute, despite a month-long expiry** (§9b). Live cleanup: found and retired the one stale, already-expired, pre-fix exception that was causing this in the real tenant (a no-op on real access, since it was already expired — just stops it from being re-scanned). ## 1. Purpose

An SoD policy names two sets of entitlements — Set A and Set B — that must never both be held by the same person at the same time. Example: "Payment Initiator" (a group) must never be held alongside "Payment Approver" (another group), because the same person should never be able to both create and approve a payment.

The engine has two halves:
- **Preventive**: blocks a *new* grant from ever completing if it would create a conflict.
- **Detective**: a live scan that reports conflicts that already exist, for any reason (including ones the preventive check never had a chance to stop).

## 2. Data model

Seven tables (migrations `0024_sod_engine`, `0025_sod_exceptions`, `0026_sod_notifications`, `0027_sod_exception_requests`, `0028_sod_notify_toggle`, `0030_sod_exc_req_shape`, `0032_sod_exc_req_assign_link`) — six actively used, one retired:

- **`sod_policies`** — `name`, `description`, `severity` (LOW/MEDIUM/HIGH/CRITICAL), `status` (ACTIVE/DISABLED).
- **`sod_policy_entities`** — one row per member of a policy's Set A or Set B. `conflict_side` is `'A'` or `'B'`. `entity_type` is one of:
  - `GROUP` — a real Entra group
  - `ROLE` — a real Entra directory role (e.g. Global Administrator)
  - `APPLICATION` — a specific app role on a specific Enterprise Application (`entity_id` = the application, `app_role_external_id` = the specific role on it)
  - `PACKAGE` — an entire AccessPilot Access Package. This is resolved **live** against the package's current items every time it's checked — never cached. If the package's items change later, the rule's meaning updates automatically with no migration needed.
- **`sod_exceptions`** — a genuinely *stored* piece of state in this engine (see §9). A formally accepted, time-boxed risk acceptance for a specific `(sod_policy_id, user_id)` pair: `justification`, `granted_by`, `expires_at`, `revoked_at`.
- **`sod_notification_settings`** — singleton config (see §16), also carrying `cooldown_enabled`/`cooldown_hours` (§10a) and `notify_on_exception_requested` (§16).
- **`sod_notifications`** — the notification log (see §16), also carrying an optional `sod_exception_request_id` so an `EXCEPTION_REQUESTED` notification can be resolved when its request is decided.
- **`sod_exception_requests`** — the other genuinely stored piece of state (see §9a): a request bridging a blocked admin assignment attempt to the exception workflow. `sod_policy_id`, `user_id`, `requested_by`, `justification`, the specific blocked entitlement (`resource_type`/`resource_id`/`app_role_external_id`), `status` (PENDING/GRANTED/DENIED), `decided_by`, `decided_at`, `denial_reason`, `sod_exception_id` (set once granted, linking to the real exception it produced) — plus, added later (`0030_sod_exc_req_shape`), the rest of the original blocked `AssignmentCreate`'s shape so a grant can recreate it exactly (§9a): `approver_id`, `fallback_approver_id`, `fallback_unlock_hours`, `assignment_type` (default `PERMANENT`), `expiration_time` — and, added later still (`0032_sod_exc_req_assign_link`), `granted_assignment_id`: the exact `AccessAssignment` the grant produced, set once at grant time, used by §9c's cascade-revoke lookups to avoid the ambiguity a purely heuristic match proved unsafe.
- **`sod_admins`** — **retired, unused** (see §3). Originally an in-app, non-Entra way to flag a directory user as `AccessPilot.SoDAdmin`; removed when that role was made Entra-only. Kept in the schema only so `Base.metadata.create_all` never needs a migration change for its removal — no service or API code reads or writes it anymore.

Violations themselves are still computed fresh on every read, never stored — the same pattern the Dashboard's other live-computed panels already use, so there is nothing that can drift out of sync with real access state. `sod_exceptions` and `sod_exception_requests` are the deliberate exceptions to "nothing is stored" in this whole engine, because a risk-acceptance decision (and the request that led to it) is inherently something that must survive across scans, not something derivable from current access state.

**Severity is a label only.** It's shown in the UI and returned in every API response, but nothing in this engine branches on it — a CRITICAL conflict can be overridden or excepted by an Admin/SoDAdmin exactly as easily as a LOW one, and severity plays no role in which rules get checked or how. It exists purely as a triage aid for whoever is reading the violations list, not as an enforcement lever. If severity-gated behavior (e.g. "CRITICAL can never be overridden") is ever wanted, that's unbuilt — a deliberate product decision, not something to infer from the field's presence.

## 3. Who can do what — a deliberate separation of duties on the engine itself

Two roles matter here:

| Role | Can view violations & rules (`SOD_READ`) | Can edit rules or grant exceptions (`SOD_MANAGE`) |
|---|---|---|
| `AccessPilot.Admin` | ✅ | ❌ |
| `AccessPilot.SoDAdmin` | ✅ | ✅ |

An Admin can see everything and read who's on it, but — just as deliberately as it cannot edit the rules — **cannot grant an exception either**: an Admin granting themselves a risk acceptance would be an equally effective way to defeat the engine as an Admin editing the rule directly, which is already forbidden. Confirmed live: an Admin attempting `POST /sod/exceptions` gets 403.

`AccessPilot.SoDAdmin` is sourced **exclusively from a real Entra App Role assignment** on the AccessPilot app registration — recognized purely from the caller's own access token (`user.roles`, in `require_authenticated_user`), exactly the same way `AccessPilot.Admin`/`AccessPilot.User` are. There is deliberately **no in-app path to grant or revoke it at all** — assigning the role happens directly in the Entra/Azure portal, outside AccessPilot entirely, and takes effect on the user's next token refresh (up to ~60 minutes, or immediately via the "Refresh my access" button on the Profile page).

**This was a real design change, not the original shape**: an earlier revision let a plain `AccessPilot.Admin` grant/revoke this flag from an in-app "SoD Administrators" roster panel (`sod_admins` table, `POST`/`DELETE /sod/admins`) with zero Entra involvement — additive to the real-Entra-role path, either one was enough. **Removed deliberately**, at the user's explicit request, after discovering a real user (John) held `SoDAdmin` purely through that in-app grant with no matching real Entra role at all: an Admin being able to grant SoD governance to anyone from inside the app, with no Entra portal access needed, was recognized as an equally effective way to defeat the engine's own separation of duties as an Admin editing rules directly (already forbidden) or granting exceptions (already forbidden, above) — the in-app roster was simply a third, previously-overlooked way to the same outcome. The `sod_admins` table/model are kept in the schema (unused, no migration) rather than dropped, to avoid a destructive schema change for what's purely a code-path removal; nothing reads or writes it anymore. John's local grant was revoked as part of this change (via the still-working service function, before it was removed, so it has a proper `SOD_ADMIN_REVOKED` audit entry) — he was the only entry in the roster at the time. **Consequence worth knowing**: if nobody in the tenant currently holds the real Entra `AccessPilot.SoDAdmin` app role, `SOD_MANAGE` becomes unreachable through the app for anyone until someone assigns it to a real user directly in Entra — there is no other in-app recovery path (an Admin cannot grant it, and Break-Glass can only ever resolve to Admin/BreakGlassAdmin, never SoDAdmin — see the Break-Glass note elsewhere in this doc set).

`AccessPilot.SoDAdmin` also has read access to Groups/Roles/Applications/Packages (not manage rights) — without it, the rule-builder's entity pickers would have nothing to show.

## 4. Validation enforced when a rule is saved

Both checked at `POST /policies` and `PATCH /policies/{id}`, before anything is written:

1. **Both sides must be non-empty** — a rule needs at least one entity on Side A and at least one on Side B, or it can never mean anything.
2. **The same entity can never appear on both sides** — the same real `(entity_type, entity_id, app_role_external_id)` tuple cannot be listed as both a Side A and a Side B member of the same policy. This would make the rule fire for literally every holder of that one entitlement — the same "baseline access" failure mode described in §7, just self-inflicted through the rule's own shape rather than a bad entity choice. Rejected with a 422 at save time, not silently accepted.
3. **A submitted duplicate within the same side is deduped**, not rejected — see §7's engineering note on why this needed to be explicit.

An exception (§9) has its own, separate validation: `expires_at` must be in the future — rejected with 422 otherwise, so an exception can never be created already-inert.

Neither policy-save check can see into a *package's* items at save time (a `PACKAGE` entity is only expanded when checked, not when saved) — so a Side A package and a Side B package that happen to share an item today is not currently caught by validation. This is a known gap, not a deliberate design choice; see §14.

## 4a. Deleting a rule — delete if unused, disable if it has history

**Real bug found and fixed live** (via a real cleanup of accumulated test data — see the session that added this section): `DELETE /sod/policies/{id}` always attempted a hard delete, which only ever worked if the policy had *never* had an exception granted against it or a notification fired for it. `sod_exceptions`, `sod_notifications`, and `sod_exception_requests` are all deliberately permanent, full-history tables (§9, §16) with a real foreign key to `sod_policy_id` and no `ON DELETE CASCADE` — so any policy with real history could never be hard-deleted at all, failing with a raw Postgres foreign-key error the caller never saw a clean message for. SQLite (the test suite's database) doesn't enforce this FK, so the bug had zero test coverage and never surfaced until it hit the real Postgres database live.

**Fix**: `delete_sod_policy()` now checks for existing history first (`sod_exceptions` / `sod_notifications` / `sod_exception_requests` rows referencing the policy). If none exist, it deletes the policy and its entities outright (with an explicit `flush()` between the two deletes — no `relationship()` exists between `SodPolicy`/`SodPolicyEntity` for SQLAlchemy to order this automatically, which was a second, related bug: even a policy that *should* be deletable could fail the same way if the entity deletes and the policy delete landed in the same flush). If history exists, the policy is set to `status: "DISABLED"` instead and returned in the response — mirroring `DELETE /packages/{id}`'s identical "delete if never used, else archive" shape exactly. A true delete returns `{"deleted": true, "id": ...}`; a disable-instead returns the disabled policy object. The same delete-then-flush-then-delete ordering bug was also found and fixed in `delete_package()` (`services/packages.py`), which had the identical pattern.

## 5. Two data sources — AccessPilot-tracked *and* direct-in-Entra

This is the most important thing to understand about how conflicts are actually detected, and the source of every "why is this flagged / why isn't this flagged" question so far.

A user's real holdings are checked two ways:

1. **AccessPilot-tracked** — an `ACTIVE` **or `ELIGIBLE`** `AccessAssignment` row (something granted *through* AccessPilot's own PIM flow). `ELIGIBLE` counts deliberately, not just `ACTIVE`: an eligible-but-never-activated grant is still a standing right the user (or an admin on their behalf) can turn real at any moment with no further review, so two conflicting items both sitting `ELIGIBLE` for the same user is exactly the state this engine exists to prevent — waiting until one of them is actually activated would be too late to have ever stopped the assignment that created the conflict. `PENDING_APPROVAL`/`SCHEDULED`/`REJECTED`/`REVOKED`/`EXPIRED` never count.
2. **Direct-in-Entra** — real membership AccessPilot's assignment engine was never involved in granting at all:
   - **Groups**: the already-synced, source-agnostic `UserGroup` table. No extra cost — this table already reflects real membership regardless of how it was granted.
   - **Roles and Application roles**: there's no synced per-user table for these, so this is a **live, on-demand Microsoft Graph read** at check time (`GET /users/{id}/memberOf/microsoft.graph.directoryRole` for roles, the existing app-role-assignments read for applications).

**Fail-open, and distinctly logged.** If the live Graph read fails (outage, throttling, a missing permission), it's treated as "nothing found" rather than blocking the grant or crashing the check — consistent with every other Direct-in-Entra read elsewhere in this app. This path logs a specific warning (`"SoD direct-in-Entra ROLE/APPLICATION check failed for user %s (treated as no match)"`) distinct from a generic Graph error, precisely because "checked, found nothing" and "failed to check, assumed nothing" look identical to the caller otherwise — the log line is the only signal that SoD enforcement was silently incomplete for that one check. This is a monitoring hook, not a behavior change: nothing currently alerts on it.

**Why direct-in-Entra checking matters**: AccessPilot's own login roles (`AccessPilot Admin` / `AccessPilot User`) are a real example of something that is *only ever* direct-in-Entra — nobody is ever granted those roles by AccessPilot's own assignment engine, since they're assigned directly in the Enterprise Application's "Users and groups" blade in Entra. Without the direct-in-Entra check, a rule referencing them would never be able to detect anything, ever, no matter how correctly it was written. (This is also exactly how a real, live violation — a user holding both `AccessPilot Admin` and `AccessPilot User` — was first found in this tenant.)

## 6. Dangling references — what happens when a referenced entity is deleted

Any entity a policy references — a `GROUP`, `ROLE`, `APPLICATION`, or `PACKAGE` — can later be deleted, either in Entra or inside AccessPilot itself. This is handled the same way for all four types, not just packages:

- **Display (`GET /policies`)**: resolving a deleted entity's name fails gracefully — the entity comes back with `entity_display_name: null` and `entity_resolved: false` instead of erroring the whole response. This is how you notice a rule has gone stale — check for `entity_resolved: false` in the policy list.
- **Enforcement (`check_sod_conflicts` / `get_sod_violations`)**: a dangling reference simply never matches anything real (there's nothing left to hold), so it degrades to "this side can never trigger" rather than raising an error. A policy with one live side and one fully-dangling side is inert, silently — it's still `ACTIVE` and still listed, but it can never actually fire. The only way to notice is the same `entity_resolved: false` flag on the display side; there's no separate alert or automatic disabling of a rule that's gone inert this way.

## 7. The mistake that's easy to make: don't put a "baseline access" role in a rule

Live debugging surfaced a real, concrete trap, worth remembering when writing any rule:

A package ("P01-Project") had three items: a group, a directory role, and — accidentally — the `AccessPilot User` application role. That last one isn't a business entitlement; it's the literal role required to sign into AccessPilot at all. Because the engine correctly checks direct-in-Entra holdings, *every single logged-in user* satisfies "holds AccessPilot User" by definition. A rule with that item on one side therefore fires for every user who has ever logged in, regardless of anything else they hold — which usually isn't what was intended.

**The lesson generalizes**: any entity you add to a rule should represent a genuine, specific business entitlement — not a role or group that describes "is a user of this system at all," "is in the default all-staff group," or similar. If a rule fires universally and that's surprising, check whether one of its items is actually a baseline/default access item rather than a real conflict condition. §4's "no entity on both sides" validation catches the same-side-shape version of this mistake; it cannot catch this version, since the universal item is only on one side and is, in isolation, a perfectly validly-shaped entity.

## 8. The three enforcement points

SoD is checked only at the moments access is actually about to become real — never at request or eligibility time. This mirrors AccessPilot's existing PIM philosophy ("nothing about real access changes until it's actually about to become real").

1. **`create_assignment()`'s bypass branch** — an Admin's direct "grant immediately" assignment. Checked before the row is even constructed; a block leaves nothing half-created. Always checked, regardless of the `check_sod_at_creation` flag below, because this is the moment real access becomes real.
2. **`activate_assignment()`** — the normal self-service Eligible → Active flow (this is what most real usage goes through, including every Access Package item). A plain end-user gets a hard block with no override. An Admin activating on someone else's behalf can pass `override_sod: true` (still requires the existing mandatory justification — no second field).
3. **The scheduled-activation worker** — the background job that activates future-dated admin grants. No interactive user is present here, so a conflict just leaves the grant `SCHEDULED` and logs it, retrying next poll rather than silently granting or crashing.

**Creation-time enforcement for admin-initiated grants (`check_sod_at_creation`)**: the ordinary (non-bypass) `PENDING_APPROVAL`/`ELIGIBLE` branches of `create_assignment()` are *additionally* checked when the caller passes `check_sod_at_creation=True` — set only by admin-initiated call sites: `POST /assignments` (Admin-only, `ASSIGNMENT_CREATE`) and `assign_package()` (Admin-only package assignment). **Self-service package requests (`request_package()`) deliberately leave this `False`** — a self-service request that would conflict still lands `ELIGIBLE` exactly as before, and is only blocked when the user actually tries to self-activate it (enforcement point 2 above). The reasoning: an Admin directly assigning something already known to conflict should find out immediately rather than watch it sit `ELIGIBLE` only to be blocked later when someone tries to activate it — but a self-service *request* isn't yet "the admin assigning something," so its behavior is unchanged. A blocked admin creation attempt returns the same `SOD_CONFLICT` 409 as the bypass branch (§12), and can be resolved via `override_sod: true` (§10) or by requesting a formal exception (§9a).

Package assignments get this for free (they funnel through the same `create_assignment`/`activate_assignment` calls per item) — but per-item override isn't supported inside a package assignment; an Admin who needs to override must use the direct Assignments UI instead.

At all three points, `check_sod_conflicts()` first excludes any conflict covered by an active exception (§9) before deciding whether to block — an excepted conflict behaves as if it isn't a conflict at all for enforcement purposes, while still being visible everywhere else (the violations list, the policy's history) as exactly what it is: a known, accepted risk, not a resolved one.

## 9. Mitigation / risk acceptance — the exception workflow

**Why this exists**: every other part of this engine treats a conflict as a hard binary — blocked, or manually overridden by an Admin *every single time* a new grant is attempted. Real compliance programs don't work that way: some conflicts are reviewed once and formally accepted as tolerable business risk for a bounded period, with the acceptance itself being the auditable record — not a repeated string of individual overrides with no memory between them. Without this, the engine either nags forever or requires an Admin to re-justify the same known risk on every single grant. This was the single largest gap found when comparing AccessPilot's SoD engine against mature IGA tools (SailPoint, Saviynt, Entra ID Governance all have an equivalent concept — "mitigating control," "risk acceptance," "SoD exception").

**Shape**: an exception is scoped to `(sod_policy_id, user_id)` — not to the specific entitlements held at the moment it was granted. The point is "this user is cleared on this rule," not "this exact pair of resources is cleared" — so it keeps applying even if which entitlement satisfies each side changes later (e.g. the user's group membership is swapped for a different group that still lands on the same side of the same rule).

**Lifecycle**:
- **Grant**: `POST /sod/exceptions` (`SOD_MANAGE`, SoDAdmin-only — see §3) with `sod_policy_id`, `user_id`, `justification` (mandatory), `expires_at` (mandatory, must be in the future). Recorded as `SOD_EXCEPTION_GRANTED` with the policy name, user, expiry, and justification in the audit metadata.
- **While active** (`revoked_at IS NULL AND expires_at > now`):
  - The **preventive check** silently lets a new grant through for that user on that rule — no repeated override needed, no `override_sod` flag required.
  - The **detective scan** still reports the violation (it's real — the user genuinely holds both sides) but marks it `exception_active: true` with `exception_expires_at`, so it reads as "known and accepted," not "needs action." Nothing disappears from view — the whole point of an auditable risk-acceptance program is that accepted risks stay visible, not that they vanish.
- **Revoke early**: `DELETE /sod/exceptions/{id}` (`SOD_MANAGE`). The very next grant attempt for that user on that rule is blocked again immediately — there's no grace period. Recorded as `SOD_EXCEPTION_REVOKED`.
- **Natural expiry**: nothing needs to run — `get_active_sod_exception()` simply stops finding it once `expires_at` has passed, since the check is a live comparison against "now," not a scheduled job flipping a status field. An expired-but-not-revoked exception stays in `sod_exceptions` forever as a historical record (`GET /sod/exceptions` shows every exception ever granted, active or not, via a computed `is_active` field — nothing is ever deleted).

**Frontend**: on `/admin/sod`, an open (non-excepted) violation row shows a plain "Open" badge — there is **no direct "Grant exception" button on this table anymore** (there used to be one; the user asked for it removed so every grant goes through one reviewable path, §9a, rather than an instant, no-approval-routing shortcut). An excepted row still shows an "Accepted until \<date\>" badge. A separate "Active Exceptions" panel lists every exception ever granted (active, expired, or revoked) with a "Revoke" action on active ones. `POST /sod/exceptions` (the direct-grant endpoint this button used to call) still exists and still works if called directly — only the UI shortcut was removed, not the API.

## 9a. Exception requests — bridging a blocked admin grant to the exception workflow

**Why this exists**: §9's exception workflow requires an SoDAdmin to proactively notice a conflict (via the violations list or a notification) and decide to grant an exception ahead of time. But with creation-time enforcement (§8) now blocking an admin's assignment attempt immediately, the admin doing the blocked assignment has no self-service path forward except `override_sod: true` (§10, a one-time bypass with no review) or asking someone out-of-band to create an exception. This closes that gap: a blocked admin can request a review instead, without unilaterally overriding the policy themselves.

**Lifecycle**:
- **Request**: `POST /sod/exception-requests` (`ASSIGNMENT_CREATE` — the same permission needed to have hit the block in the first place, so only someone who could have created the assignment can ask for an exception to it), with `sod_policy_id` (from the `SOD_CONFLICT` error's `details.conflicts`), `user_id`, `justification`, the specific blocked entitlement (`resource_type`/`resource_id`/`app_role_external_id`), and — new — the **rest of the originally-blocked `AssignmentCreate`'s shape**: `approver_id`, `fallback_approver_id`, `fallback_unlock_hours`, `assignment_type` (default `PERMANENT`), `expiration_time`. Only the direct Assignments form populates `approver_id`/`assignment_type`/`expiration_time` today (it has no fallback-approver field); `fallback_approver_id`/`fallback_unlock_hours` exist on the schema for completeness but nothing sends them yet. Creates a `PENDING` `sod_exception_requests` row and immediately fires an `EXCEPTION_REQUESTED` notification (not via §16's reconciliation pass — a request is a discrete event, not a derived condition) and an `SOD_EXCEPTION_REQUESTED` audit entry.
- **Grant**: `POST /sod/exception-requests/{id}/grant` (`SOD_MANAGE`, SoDAdmin-only, same reasoning as §9's grant gate) with `expires_at`. Creates a real `sod_exceptions` row (§9) scoped to `(sod_policy_id, user_id)` exactly as if granted directly, sets the request's `status` to `GRANTED` and `sod_exception_id` to the new exception's id, and resolves the open notification.

  **Recreates the original blocked attempt exactly, by calling `create_assignment()` itself** — not a bespoke insert — using the stored approver/fallback/duration fields and the original requester's identity (`requested_by`, resolved back to their `external_id`) as the actor. This means the exact same approval-required/no-approver branching applies as any other admin-initiated assignment: **if the original attempt had an `approver_id` set, granting produces a `PENDING_APPROVAL` row routed to that same approver — not a bare `ELIGIBLE` row** — and only that approver's own decision (the ordinary `POST /assignments/{id}/approve`/`reject` flow, unchanged) makes it `ELIGIBLE` for the end user. If there was no approver, granting lands directly on `ELIGIBLE`, as a no-approver `create_assignment()` call always does. This replaced an earlier, simpler revision that always produced a bare `ELIGIBLE` row regardless of whether the original attempt had an approver — the user explicitly asked for fidelity to the original request's approval routing instead.

  `create_assignment()` is called with `check_sod_at_creation=True`, so it still runs its own SoD check — needed because a single blocked attempt can be caught by *more than one* conflicting policy at once (the frontend files one exception request per conflicting policy). Three outcomes:
  - **Created** (no remaining conflicts) → the assignment is created (`ELIGIBLE` or `PENDING_APPROVAL` per the above), with the same notifications and audit trail `create_assignment()` always produces. The requesting admin's own notification says the user now has "eligible access" or "a pending-approval request... routed to the configured approver," whichever applies.
  - **Still blocked** (a conflict from a *different*, still-ungranted policy remains — `create_assignment()` itself raises `SOD_CONFLICT`) → nothing is created. The requesting admin's notification says so explicitly instead of falsely claiming success — they need to request (and get granted) an exception for that policy too.
  - **Failed** (some other error — e.g. the original requester's account or the target application role no longer exists) → nothing is created; the requesting admin's notification names the failure and says to create it manually.

  Either way, an `EXCEPTION_REQUEST_GRANTED` notification goes to the requesting admin specifically (`exception_request.requested_by`) through the **general, per-user notification system**, not the shared `sod_notifications` log, since this is addressed to one specific person, not "anyone with `SOD_READ`."
- **Deny**: `POST /sod/exception-requests/{id}/deny` (`SOD_MANAGE`) with an optional `reason`. Sets `status` to `DENIED`, records the reason, resolves the notification. No exception is created, nothing is created for the user. Also notifies the requesting admin (`EXCEPTION_REQUEST_DENIED`, general notification system, includes the reason if one was given).
- Only a `PENDING` request can be granted or denied — deciding an already-decided request returns 409 (`REQUEST_ALREADY_PROCESSED`).

**Frontend**: the Assignments admin "Add assignment" form shows a "Request SoD Exception" button next to the error message when creation is blocked with `SOD_CONFLICT` — it submits one exception request per conflicting policy, reusing the assignment form's own justification text. `/admin/sod` has an "Exception Requests" panel (visible to everyone with `SOD_READ`, Grant/Deny actions SoDAdmin-only) listing every request with its status. Copy throughout no longer says "retry" — granting is the terminal action for the common (single-policy) case.

**Not currently wired for package assignments** — `assign_package()`'s per-item failures are reported back as `PackageAssignItemResult` rows with an `error_code` but no policy-id detail, so there's nothing for a "Request exception" button to act on for a package item today. The direct Assignments form is the only place this button exists; an Admin blocked on a package item must fall back to `override_sod` via the direct Assignments UI, or ask an SoDAdmin to grant an exception directly via §9.

## 9b. Revoking or expiring an exception now also ends the specific access it covered

**Why this changed**: the original design (§9/§16) deliberately never touched real access on revoke or expiry, reasoning that `SodException` is scoped to `(policy, user)`, not a specific resource, so there was "nothing a background job could safely revoke on its own." In practice this meant clicking "Revoke" on an exception — or just letting one expire — only ever blocked *future* grants; the specific access it had let through kept running indefinitely with no way to end it except a manual admin revoke of the assignment itself. The user tested this directly and asked for both: "revoke means revoke from eligible and active both, it doesn't matter" (manual revoke), and "if the grant is 4 min [but the assignment's own activation is 3 hr], it must revoke in 4 min" (expiry).

**How the covered assignment is found**: `SodException` itself still has no resource-specific column (unchanged) — but an exception granted through the exception-*request* workflow (§9a) has an indirect link back to exactly what it was granted to cover, via `SodExceptionRequest.sod_exception_id` (set when the request is granted) plus that request's own `granted_assignment_id` (see §9c — an exact link to the one assignment `create_assignment()` produced). `_find_exception_granted_assignment()` (`services/sod.py`) follows that chain. An exception granted through the older, untargeted `POST /sod/exceptions` path has no request behind it at all, so this correctly finds nothing and behaves exactly as before (notify-only) — that carve-out is deliberate and unchanged.

**Display-only companion field**: an eligible row time-boxed by a live exception used to still show "No activation deadline" (§17's frontend text), since that label only ever considered the assignment's own `assignment_type`/`expiration_time`, never a covering exception's `expires_at`. `get_sod_exception_covering_assignment()` (`services/sod.py`) is the mirror-image lookup — given an assignment, is there a currently-live (not revoked, not expired) exception it depends on, found the same way as §9c describes. `hydrate_display_fields()` (`assignments.py`) populates a `sod_exception_expires_at` field on every assignment response with this; the "Eligible access" list (`MyAccess`, `src/App.tsx`) shows "Eligible until the SoD exception expires (&lt;date&gt;)" instead of "No activation deadline" whenever it's set. Purely informational — the real gate is always the live `check_sod_conflicts()` call at activation time, never this field.

**`_revoke_assignment_for_lapsed_exception()`** (`services/sod.py`) does the actual work once a target assignment is found — mirrors `revoke_assignment()`'s (`assignments.py`) `ACTIVE`-vs-not branching (removes the real Entra/Graph grant first if it was genuinely `ACTIVE`, then sets `REVOKED`), but is its own function rather than a call to `revoke_assignment()` because this can run with **no live human actor at all** (the background worker case, below) and needs SoD-specific wording instead of the generic "revoked by an administrator" message. Fires a personal `SOD_EXCEPTION_LAPSED` notification to the affected user (`"Your access was automatically revoked because the SoD exception covering \"<policy>\" was revoked / expired."`) and an `ASSIGNMENT_REVOKED` audit entry (`metadata.reason = "SOD_EXCEPTION_LAPSED"`).

**Two trigger points**:
- **Manual revoke** — `revoke_sod_exception()` calls this synchronously, right after marking the exception `revoked_at`, in the same `DELETE /sod/exceptions/{id}` request. Immediate, no polling delay.
- **Expiry** — a new background worker, `sod_exception_expiry_worker_loop` (`workers/sod_expiry.py`, started in `main.py` alongside the sync/expiration/activation workers), polls every **60 seconds** for any non-revoked exception whose `expires_at` has passed and calls `revoke_lapsed_sod_exceptions()`. This runs regardless of whether anyone has the app open — unlike §16's reconciliation pass, which only runs when a signed-in Admin/SoDAdmin's browser happens to poll `GET /sod/notifications`. Idempotent per-exception (once its own linked assignment is revoked, `_find_exception_granted_assignment` finds nothing left to do for it — see §9c for why that requires an exact link, not just "no longer ELIGIBLE/ACTIVE").

**Effect on `EXCEPTION_EXPIRED` (§16)**: since the worker above now resolves a request-based exception's expiry within 60 seconds, `get_sod_violations()` normally no longer shows that conflict as open by the time the reconciliation pass would otherwise flag it — so `EXCEPTION_EXPIRED` now effectively only fires for the narrower legacy case (an untargeted, directly-granted exception with nothing to auto-revoke) or the rare race window before the next worker tick. Its message was reworded from an unconditional "the real access was NOT automatically revoked" to "this one wasn't automatically revoked," since the blanket claim is no longer true in general.

## 9c. Finding "the assignment this exception covers" precisely, not heuristically

**Why this exists**: §9b's cascade-revoke needs to find, given a `SodException`, the one specific `AccessAssignment` it was granted to cover. Two matching approaches were tried, in order, as live testing found real problems with each:

1. **First attempt — match by (user, resource, status), unordered.** Broke immediately: an old, wholly unrelated `ELIGIBLE` assignment for the same target (e.g. a leftover from an earlier, unrelated grant of the same group) could be picked over the real one, since an unordered query has no way to prefer one match over another. Confirmed live — a weeks-old leftover got revoked instead of the row that mattered.
2. **Second attempt — same match, plus `created_at >= request.created_at` (with a small grace window for clock jitter) and `ORDER BY created_at ASC`.** Fixed the first bug, but broke differently one grant later: this filter has a lower time bound but no upper one. Once an exception's own original assignment had been revoked, its query would happily keep matching the *next* `ELIGIBLE`/`ACTIVE` assignment for that same target it could find in the future — even one produced by a completely different, later grant — because nothing ever marks a naturally-expired `SodException` as "done." `revoke_lapsed_sod_exceptions()` re-scans every non-revoked, past-expiry exception on **every single 60-second tick, forever** — so an old, already-handled exception sitting in that scan set indefinitely was a live landmine for any future grant to the same target. Confirmed live: granting a fresh, month-long HR-Team exception got it auto-revoked within about a minute, because an old exception's expired-and-forgotten row (from an entirely separate, earlier test) re-matched the brand new assignment as if it were its own.

**The actual fix — an exact link, not a heuristic**: `SodExceptionRequest.granted_assignment_id` (new column, migration `0032_sod_exc_req_assign_link`) is set exactly once, at the moment a request is granted, to the `AccessAssignment.id` that `create_assignment()` just returned (`grant_sod_exception_request()`, `services/sod.py`). `_find_exception_granted_assignment()` and its mirror `get_sod_exception_covering_assignment()` now look this up directly — `session.get(AccessAssignment, request.granted_assignment_id)`, returning it only if still `ELIGIBLE`/`ACTIVE` — with **no ambiguity possible, ever, regardless of how much later a different grant for the same target happens**. The old (user, resource, timing) heuristic is kept only as a fallback for requests granted before this column existed; every new grant going forward never touches that path at all. A regression test (`test_a_later_unrelated_grant_for_the_same_target_survives_the_old_exceptions_worker_tick`) reproduces the exact live scenario: a short-lived first grant gets processed by the worker, then a second, unrelated month-long grant for the same target is made, and a simulated next worker tick confirms the second grant survives untouched.

**Live cleanup performed**: one stale, already-expired, pre-fix `SodException` was found in the real tenant with exactly this landmine shape (a `granted_assignment_id`-less request whose own original assignment was long gone) and was formally marked `revoked_at` directly — a no-op on real access, since it was already past its own expiry and covering nothing, but it stops the worker from ever re-scanning it again.

## 10. Overriding a block (distinct from an exception)

`override_sod: true` on `AssignmentCreate` (Admin-only path, since it's only checked in the bypass branch) or `AssignmentActivate` (checked server-side against `actor_roles` — only honored when the caller is an Admin, never for a plain end-user activating their own access). This is a **one-time, per-grant** decision with no memory — the opposite of §9's exception, which is a standing decision covering every future grant until it expires or is revoked. Use an override for a one-off "this specific grant needs to happen right now despite the conflict"; use an exception for "this user/rule combination is a known, ongoing, accepted risk." Either way, the existing mandatory justification field is reused — there's no separate field for the override's reason. An override is recorded on the resulting audit entry (`sod_override: true`).

## 10a. Cooldown — closing the deactivate-then-activate-the-other-side gap

**Why this exists**: every check in this engine (§5) looks at *simultaneous* holdings — does the user hold both sides *right now*. This is a real, named limitation shared by mature IGA tools, not unique to AccessPilot: a user (or an Admin acting for them) could deactivate side A, then immediately activate side B — at no instant did they hold both, so nothing was ever blocked — then later deactivate B and reactivate A, cycling between the two sides of a conflict without ever technically violating it. Confirmed live as a real, reproducible behavior in this tenant.

**How it works**: `sod_notification_settings.cooldown_enabled` (default off) and `cooldown_hours` (default 24) gate an additional check inside `check_sod_conflicts()`. When enabled, in addition to "does the user hold the opposite side right now" (`_user_holds_any`), it also checks "was the opposite side recently deactivated or revoked" (`_recently_deactivated_or_revoked`) — a query against `AuditLog` for `ASSIGNMENT_DEACTIVATED`/`ASSIGNMENT_REVOKED` entries on the user's own `AccessAssignment` rows within the last `cooldown_hours`, joined via the audit entry's `target_id`. The audit log is reused rather than adding a new timestamp column, since `deactivate_assignment()` doesn't otherwise track "when did this get deactivated" anywhere queryable. Either condition being true blocks the grant exactly like a live simultaneous conflict would (still subject to an active exception, §9, taking precedence).

**Scope**: this closes the cycling gap for the specific case of a user deactivating/revoking one side and then trying to activate the other within the window — it does not, and cannot, catch a conflict that never touches AccessPilot's own deactivate/revoke path (e.g. an admin removing direct-in-Entra group membership through the Entra portal itself, bypassing AccessPilot entirely — there's no audit trail for that here to key off of).

**Configuration**: `/admin/sod/configuration`'s notification-settings form (SoDAdmin-editable, Admin read-only, same gating as the rest of §16) now includes the cooldown toggle and the hours field (1–720).

## 11. Preventive check vs. detective scan — a deliberate performance split

- For a rule made entirely of **GROUP** entities, the detective scan (`GET /sod/violations`) stays on a pure-database path (`AccessAssignment` + `UserGroup`) — fast, no Graph calls, scales to any tenant size.
- The moment a rule has a **ROLE or APPLICATION** entity on either side, there's no cheap synced table to lean on the way `UserGroup` allows for groups — so the detective scan falls back to checking *every* directory user's live Entra state for that specific rule. This is correct but costs one or two Graph calls per user per such rule. In this tenant (a handful of real users) it takes a few seconds; it has not been optimized for a tenant with thousands of users — a future improvement would batch or cache the Graph reads instead of one call per user.
- The **preventive** check never has this problem — it only ever checks the *one* user attempting the *one* grant, so it's always cheap regardless of entity type. The exception lookup (§9) adds one small indexed query per matched conflict — negligible.
- **The Dashboard's violation-count widget triggers its own independent scan** — it calls the same `GET /sod/violations` the SoD page does, on every Dashboard load, with no caching or sharing of results between the two. There is no caching layer anywhere in this app for any live-computed endpoint, so this cost is real and compounds with the point above.

## 12. Error contract

A blocked grant (any of the three points in §8, when no active exception applies) returns HTTP 409 with:

```json
{
  "error": {
    "code": "SOD_CONFLICT",
    "message": "This grant conflicts with Separation-of-Duties policy: <name>.",
    "requestId": "...",
    "details": {
      "conflicts": [
        {"policy_id": "...", "policy_name": "...", "severity": "HIGH"}
      ]
    }
  }
}
```

`POST /sod/check` (the non-blocking pre-check) returns 200 with the full policy objects, not just names/ids:

```json
{ "conflicts": [ /* SodPolicyResponse objects, same shape as GET /policies entries */ ] }
```

An empty `conflicts` array means no conflict was found — it does not distinguish "genuinely no conflict," "a Graph read failed and fell back to no-match" (§5), or "a conflict exists but is covered by an active exception" (§9); none of those are visible in this response, only in the backend logs or by separately checking `GET /sod/exceptions`.

A validation failure at policy or exception save time (§4) returns a generic 422 (`VALIDATION_ERROR`, `"The request contains invalid data."`) — the same generic shape every Pydantic validation failure in this app returns; the specific reason is not surfaced in the response body today.

## 16. Notifications

**Why this exists**: even with the mitigation workflow (§9), discovery was still entirely passive — a new violation or a soon-expiring exception was only visible to someone who happened to open the Dashboard or the SoD page. This was the second-biggest gap named in the industry-standard assessment, right after mitigation.

**Five notification types**, most independently toggleable via `sod_notification_settings` (a singleton, same get-or-create pattern as `SecuritySettings`/`BrandingSettings`; all default ON, 7-day exception-expiry warning):
- `NEW_VIOLATION` — a user now holds both sides of an active rule. Reconciliation-driven (below).
- `EXCEPTION_EXPIRING` — an active exception (§9) is within `exception_expiring_warning_days` of `expires_at`. Reconciliation-driven.
- `EXCEPTION_EXPIRED` — an exception's own `expires_at` has already passed while the conflict it was covering is *still* real despite that — see §9b below for why this now only fires in the narrower case where nothing could be auto-revoked. Reconciliation-driven, gated by the same `notify_on_exception_expiring` toggle as the warning above (no separate setting).
- `EXCEPTION_REQUESTED` — an admin requested an exception for a blocked assignment (§9a). **Eager, not reconciliation-driven** — created the instant `POST /sod/exception-requests` succeeds, gated by its own `notify_on_exception_requested` toggle (checked inline in `create_sod_exception_request()`, not by `reconcile_sod_notifications()`) since a request is a discrete event, not a derived condition to diff against reality.
- `EXCEPTION_REQUEST_GRANTED` / `EXCEPTION_REQUEST_DENIED` — sent to the *requesting admin* specifically (not the shared SoD log) when their request is decided (§9a). Eager, same reasoning as `EXCEPTION_REQUESTED`, delivered through the general per-user notification system (`docs/20_NOTIFICATIONS.md`) instead.

**How reconciliation works** (`reconcile_sod_notifications()` in `services/sod.py`, covers `NEW_VIOLATION`/`EXCEPTION_EXPIRING`/`EXCEPTION_EXPIRED`): for each enabled check, it computes what's currently true (`get_sod_violations()` for the first and third; `sod_exceptions` queries for the second and third — the violations list is computed **at most once per pass** and reused by both the first and third checks, to avoid doubling the expensive per-user Graph scan when both settings are on), diffs that against currently-*open* (`resolved_at IS NULL`) `SodNotification` rows for the same `(policy_id, user_id)` or exception id, creates a new row for anything newly true, and marks `resolved_at` on anything that's no longer true (the violation was fixed; the exception was revoked, renewed by a fresh one, or is no longer within the warning window). This means:
- **No duplicate notifications** — calling reconciliation twice in a row with nothing changed produces zero new rows.
- **Auto-resolution** — fixing a violation (or revoking the exception that was about to expire) resolves the corresponding notification the next time reconciliation runs, with no separate "close this notification" action needed.
- **Full history retained** — nothing is ever deleted; `is_active`-style state is entirely derived from `read_at`/`resolved_at` being null or not.

**Deliberately NOT wired into `GET /sod/violations` or the Dashboard widget** — those are already the expensive path for ROLE/APPLICATION rules (§11), and reconciliation would double that cost on every Dashboard view. Instead it runs exactly once, at the top of `GET /sod/notifications` — which is what the SoD Configuration page and the topbar Bell's unread-count fetch both call. **Confirmed live**: with APPLICATION-based rules in this tenant, a full reconciliation pass currently takes ~15 seconds (the same per-user Graph-scan cost from §11, now paid once per `GET /sod/notifications` call instead of scattered across every violations read) — this does not block page rendering (the Bell badge just appears a few seconds after the rest of the page), but it is a real, felt delay worth knowing about, and would need the same batching/caching fix §11 already flags if this ever needs to feel instant.

**"Live" delivery — background polling, not push**: since this app has no WebSocket/SSE infrastructure (the Dashboard's own "real-time" feel is the same technique — a plain interval timer), notifications become live the same way: the topbar Bell (rendered by the persistent `Shell` chrome, so it's running regardless of which page is open) polls `GET /sod/notifications` every **60 seconds** for every Admin/SoDAdmin session — deliberately slower than the Dashboard's 30s, specifically because this call pays the ~15s reconciliation cost above on every single tick, continuously, for the life of the session; 30s would leave the Graph-scan running almost back-to-back. The SoD Configuration page's own notification-log panel polls the same endpoint on the same 60s cadence (opening that page doesn't add a second concurrent reconciliation pass beyond what the Bell is already doing). Separately, the "Exception Requests" panel on `/admin/sod` polls `GET /sod/exception-requests` every 20 seconds — much faster, since that's a single indexed table read with no reconciliation and no Graph calls, so a pending request becomes visible to a watching SoDAdmin quickly without inheriting the NEW_VIOLATION path's cost.

**Read state is global, not per-viewer** — `read_at` is a single flag on the notification row, not tracked per-Admin/SoDAdmin. Whoever marks it read marks it read for everyone. This matches the small-team scale this app targets; a larger deployment with multiple independent SoDAdmins might want per-viewer read state, which isn't built.

**No delivery beyond in-app** — there is no email, Teams, webhook, or any other outbound channel. `sod_notifications` is purely a log an Admin/SoDAdmin has to actually open the app to see (via the Bell badge or the Configuration page) — nothing pushes to anyone. This was a deliberate scope decision: this app has no email/SMTP infrastructure at all today, so real delivery would be new infrastructure, not an extension of an existing pattern.

## 17. What's deliberately not built yet

- **No multi-way (>2-set) rules** — every rule is exactly two sides.
- **No severity-gated enforcement** — see §2; severity is a label only.
- **No cross-package overlap detection at save time** — see §4's last paragraph.
- **Detective scan doesn't scale-test at large tenant size, and the Dashboard widget doesn't cache/share it** — see §11; §16's reconciliation pass inherits the exact same cost.
- **No outbound notification delivery** (email/webhook/etc.) — see §16's last paragraph.
- **No per-viewer notification read state** — see §16.
- **No versioning or change history on rules themselves** — there is no way to answer "what did this rule say at the time a since-resolved violation occurred." Every edit overwrites the rule's entities in place with no record of the prior shape. (Exceptions and notifications, by contrast, now have full history — see §9, §16 — this gap is specifically about `sod_policies`/`sod_policy_entities`.)
- **Cooldown only catches AccessPilot's own deactivate/revoke path** — see §10a's scope note; a direct-in-Entra change made outside AccessPilot leaves no audit trail to key off of.
- **No exception-request flow for package assignments** — see §9a's last paragraph; only the direct Assignments form's blocked-creation case has a "Request SoD Exception" button today.
- **Auto-revoke on exception revoke/expiry (§9b) only covers request-based exceptions** — an exception granted through the older, untargeted `POST /sod/exceptions` path still has nothing specific to revoke and stays notify-only (§16's `EXCEPTION_EXPIRED`), since it was never granted for one specific resource. This is the one remaining case that behaves the way the *whole* engine used to.
- **No real push delivery for notifications** — see `docs/20_NOTIFICATIONS.md`; "live" means short-interval polling (10s personal / 60s SoD), not instant push. A genuinely instant experience would need a new SSE-based delivery mechanism, considered and deliberately deferred.
- **A pre-existing violation found only by the detective scan has no in-app path to an exception at all** — a real consequence of removing the Violations table's direct "Grant exception" button (above): the exception-*request* workflow (§9a) is built around a live blocked-creation attempt (it needs a specific `resource_type`/`resource_id` that was just rejected), not an arbitrary already-existing violation the scan happened to find. Today, excepting a scan-found violation requires calling `POST /sod/exceptions` directly (still a working API, just with no UI entry point) — a future revision could let an SoDAdmin start a request straight from a Violations row instead.
