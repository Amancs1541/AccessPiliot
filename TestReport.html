Headline findings

  • Verified live on Entra: create-disabled account, enable, department push (Mover), manager push, disable (Leaver), duplicate rejection and delete. The throwaway account was deleted and confirmed gone.
  • Two bugs found and fixed on fucking.new@workamanvgmail.onmicrosoft.com: (1) the leaver process had run once, then the account was re-enabled directly in Entra; AccessPilot's internal flag never cleared, permanently blocking a new Start-leaver-process attempt and the deletion worker alike — fixed by keying both off the account's CURRENT status, not the historical flag. (2) Even after fix (1), calling the endpoint directly proved the backend logic worked, but the button in the browser still did nothing — because it relied on window.prompt()/window.confirm() for the justification, which silently returns null with no dialog shown at all in some embedded/webview browser contexts. Every leaver/re-enable justification and approval-note input (Start leaver process, Run now, Approve/Deny, request-to-re-enable) was rebuilt as a proper inline form with a textarea and buttons — no native browser dialogs anywhere in this flow. Verified live end-to-end against the real account: request created, real Entra account disabled, notification delivered to the approver (a real PENDING request now awaits "Test-User"'s decision on this real account).
  • Not fixable in code: Inactive-users review scope. Microsoft returns 403 for signInActivity because the tenant lacks Entra ID P1/P2, not because of AuditLog.Read.All.
  • Entra is eventually consistent: a read right after a write can return stale data (my first live run misreported failures for this reason). Any code that verifies a write by reading straight back should retry.
  • Not verified: the browser UI beyond a clean TypeScript build (no authenticated browser session available here), and Okta (not connected; only unit-tested through the shared connector interface).

Leaver workflow: manual start with approval, re-enable approval, account deletion, PDF report 20/20 passed

Review. After the leaver process, enabling an account needs a written reason and the manager's approval (lifecycle owners when there is no manager; admins can override, nobody approves their own request). Policies can delete accounts from every IdP N days later; the person stays as 'Deleted' with an audit record. A PDF report covers all JML processes. Manual 'Start leaver process now': justification (min. 10 chars), accounts disabled immediately in every IdP, manager approval (lifecycle owners as fallback, initiator cannot decide), approved = leaver process runs, denied = only the accounts that were active are enabled again and the initiating admin is notified. If no directory can disable the account no request is created. Sync now alerts when a processed leaver is enabled directly in the directory. Both approve and deny paths verified live against Entra.

Improvement suggestions

  • A leaver enabled directly in Entra (bypassing AccessPilot) is only alerted, not auto-disabled: decide whether to auto re-disable.
  • Approvers only see requests in My Access Reviews / Movers; add e-mail or Teams notification for urgent leavers.
  • Approved re-enable restores accounts only, not the revoked access; consider an optional 'restore previous access' step.
  • Directory sync could re-enable a leaver's account if someone enables it directly in Entra; add an alert when a processed leaver is seen ACTIVE again.
  • Deletion is irreversible (Entra keeps users 30 days): consider a warning notification a few days before deletion.
  • PDF lists up to 500 rows per section; add date filters for large tenants.
